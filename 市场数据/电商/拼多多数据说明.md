# 拼多多搜索页数据集（2026-10-21 快照）

采集时间：2026-10-21 16:00–16:22（北京时间）。
数据源：`mobile.yangkeduo.com/search_result.html`，需登录态。
采集方式：Playwright + CDP 监听 `POST /proxy/api/search` 响应体。

原始/清洗文件：`pdd-{waterheater,dishwasher,dryer,integratedstove}.csv`，
共 480 条。清洗脚本 `scripts/build_pdd_csv.py`。

## 为什么必须用 CDP 而不是解析 DOM

拼多多移动端搜索页是 XRender 同构渲染。实测：

```js
document.querySelectorAll('a').length        // 0 个 <a> 标签
document.body.innerText.length               // 1,932（卡片是 canvas/图片）
```

商品链接根本不在 DOM 里，`document.querySelectorAll('a[href*="goods_id"]')` 返回 0。
`window.rawData` 只有 `{stores: ...}`，也没有商品列表。

唯一可靠路径：CDP `Network.enable` + 监听
`POST https://mobile.yangkeduo.com/proxy/api/search` 的响应体，
商品在 `items[].item_data.goods_model`。

**注意**：`Network.getResponseBody` 对同一 `requestId` **只能读一次**，
第二次会报 "SyntaxError: [object Object] is not valid JSON"（实际是读不到）。
必须在 `responseReceived` 事件里立即读取。

## 三个口径陷阱

### 1. `sales` 字段不可用，必须用 `sales_tip`

`goods_model.sales` 看起来像销量，实测与页面展示严重不一致：

| 页面展示 `sales_tip` | API `sales` |
|---|---|
| 总售1500+件 | 431 |
| 已抢1000+件 | 1716 |
| 已拼54.7万+件 | 100000 |
| 已抢3928件 | 53000 |
| 总售3.6万+件 | 9042 |

`sales` 既不是商品销量也不是店铺销量，且被封顶在 100,000。
**本数据集完全丢弃 `sales`，只保留 `sales_tip` 原文并解析出下界。**

### 2. `sales_tip` 有多种主语，口径不明

实测出现 6 种前缀：

| 前缀 | 出现次数（热水器） | 口径 |
|---|---|---|
| `已拼` | 59 | 商品级 |
| `已抢` | 71 | 商品级（大促话术） |
| `总售` | 48 | 商品级 |
| `热卖` | 9 | 商品级 |
| `N人想拼` | 1–23 | **不是销量**，是收藏/意向 |
| `本店已拼` / `品牌热销` | 本次未出现 | 店铺级 / 品牌级 |

`N人想拼` 已识别为无口径（`口径` 列为空），不可当销量。

### 3. 排序参数正确传入，但结果不按展示值降序

实测请求体里 `sort: "_sales"` 确实存在：

```json
{"source":"search","sort":"_sales","q":"热水器","page":2,"size":50,...}
```

但返回顺序并不按 `sales_tip` 降序。第 2 页前 8 条为：

```
已拼6件 / 已拼2.7万+件 / 已抢936件 / 已抢1000+件 / 已抢10万+件 / 已抢275件 / 已拼3件 / 已拼5.4万+件
```

可能的解释：排序依据是 API 的 `sales` 字段（已证明与展示值不一致），
而不是展示值。**因此本数据集的「排序位」不可作为热度位次使用。**

这是三个平台里**唯一一个排序不可信**的数据源。

## 字段说明

| 字段 | 口径 |
|---|---|
| `关键词` | 热水器 / 洗碗机 / 干衣机 / 集成灶 |
| `排序位` | 抓取顺序，**不可当热度位次**（排序未按展示值生效） |
| `商品ID` | `goods_model.goods_id` |
| `标题` | `goods_model.goods_name` |
| `销量展示` | `goods_model.sales_tip` 原文 |
| `口径` | 商品 / 店铺 / 品牌 / 空（`N人想拼` 为空） |
| `销量下界_件` | 从展示值解析，`54.7万+` → 547000 |
| `是否区间` | 1 = 带 `+`，是下界 |
| `价格_元` | `goods_model.price_info`（券后价，字符串） |
| `店铺ID` | `goods_model.mall_id` |
| `是否广告` | 保留字段，当前不可靠（见下） |

## 已知缺陷

1. **`是否广告` 不可靠**。`goods_model.ad` 是对象，空对象 `{}` 也为真，
   `adid` 又全部有值（120/120），无法区分广告位。该列**不要用于过滤**。
2. **采集深度不一**。热水器 200 条（10 页），干衣机 100 条（5 页），
   洗碗机 80 条，集成灶 100 条。滚动次数相同但响应数量不同，是前端懒加载节流导致。
3. **`total` 上限 300**。API 返回 `total: 300`，即每个关键词最多 15 页。
4. **无品牌字段**。需从标题前缀 `【美的】`、`美的` 等人工/正则提取，
   本数据集未做品牌归一。

## 能回答什么

1. **商品级价格分布**。拼多多是三个平台里价格字段最完整的（无打码、无区间）。
2. **标题结构与卖点**。`【品牌】` 前缀、`一级能效`、`出租房`、`上门安装` 等高频词。
3. **供给侧商品数量**。某品类下有多少商品在售（受 `total≤300` 限制）。

## 不能回答什么

- **销量排序、热度梯队**。排序未按展示值生效，`排序位` 无意义。
- 销量绝对值、市场份额。`sales_tip` 是区间下界且口径混排，不可相加。
- 品牌份额。未做品牌归一，且 `mall_id` 与品牌非一一对应。

## 复现

```sh
# 1. Playwright 打开 mobile.yangkeduo.com 并登录
# 2. CDP Network.enable → 打开 search_result.html?search_key=X&sort_type=_sales
# 3. 滚动 12 次（每次 3000px，间隔 3.4s）→ 收集所有 /proxy/api/search 响应
# 4. 写入 TSV → 清洗
uv run python3 scripts/build_pdd_csv.py
```

## 引用规范

引用时必须写明：

1. 平台是**拼多多**，不是全渠道；
2. 口径是**页面展示的「已拼/已抢/总售」**，是累计区间下界，不是档期销量；
3. **不可引用排序位次**（排序未生效）；
4. 样本是**滚动加载的 5–10 页**，不是全量。
